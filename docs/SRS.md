# Software Requirement Specification (SRS)
## Smart QR-Based Digital Canteen Coupon Management System — "My Union Canteen"

Version 1.0 · 2026-07-23

---

## 1. Introduction

### 1.1 Purpose
This document specifies the functional and non-functional requirements for a QR-code-based digital canteen coupon management system that ensures a factory pays its canteen vendor only for meals actually consumed by workers, rather than for all workers regardless of usage.

### 1.2 Scope
The system covers:
- A worker-facing Android-first mobile app for scanning a permanent canteen QR code and redeeming meal coupons.
- A canteen-facing real-time dashboard that displays worker/coupon details on every scan.
- An admin web dashboard for worker, coupon, shift, menu, and holiday management, plus reporting and analytics.
- A backend API and database enforcing coupon allocation, shift-based redemption windows, and duplicate-use prevention.

### 1.3 Definitions
| Term | Meaning |
|---|---|
| Coupon | A monthly entitlement unit for one meal category (Breakfast+Tea, Meal, Tea) |
| Redemption / Scan | The act of consuming one coupon via QR scan + confirmation |
| Shift | 1st, 2nd, or 3rd rotating work shift, each with its own meal windows |
| Meal Window | The time range during which a coupon type is valid for a given shift |
| Clock Number | Worker's unique employee/badge ID, used as the login identifier |

### 1.4 Stakeholders
- Factory Workers (coupon consumers)
- Canteen Staff (scan/dashboard operators)
- Factory HR / Admin (worker & coupon management)
- Factory Finance (billing reconciliation with canteen vendor)
- Canteen Vendor (paid based on system-reported consumption)

## 2. Overall Description

### 2.1 Product Perspective
A three-tier system: mobile app + admin web app (clients) ↔ NestJS REST/WebSocket API ↔ PostgreSQL/Redis. The canteen dashboard is a browser page (part of the admin web app, restricted role) showing real-time scan events pushed over Socket.IO.

### 2.2 User Classes
| Role | Access |
|---|---|
| Worker | Mobile app only: login, scan QR, view coupons/history, submit feedback |
| Canteen Staff | Read-only real-time scan dashboard |
| Admin / HR | Full admin dashboard: worker, coupon, shift, menu, holiday management, reports |
| Super Admin | Admin rights + system configuration, user role management, audit logs |

### 2.3 Operating Environment
- Mobile: Android 8+ (primary), iOS 13+ (secondary), via React Native/Expo.
- Admin/Canteen dashboard: modern desktop/tablet browsers (Chrome, Edge, Safari).
- Backend: containerized (Docker), deployable to Kubernetes; PostgreSQL 15+, Redis 7+.

### 2.4 Assumptions & Constraints
- One physical canteen QR code per canteen location, statically printed/displayed, never rotated (scan identifies canteen location + timestamp, not the worker — the worker's identity comes from their authenticated app session).
- Workers are pre-registered by HR with clock number, department, and default shift; shift can be updated by admin as rotations change.
- Network connectivity is assumed at the canteen for online verification; a future release should add offline QR verification (see §9 Future Features).

## 3. Shift & Meal Window Configuration

| Shift | Meal | Window |
|---|---|---|
| 1st | Breakfast + Tea | 08:30 – 09:30 |
| 1st | Lunch (Meal) | 11:30 – 14:00 |
| 1st | Tea | 14:30 – 15:30 |
| 2nd | Breakfast + Tea | 16:30 – 17:30 |
| 2nd | Dinner (Meal) | 19:30 – 21:30 |
| 3rd | Tea | 01:30 – 02:30 |
| 3rd | Breakfast + Tea | 03:30 – 04:30 |

Notes:
- 2nd shift has no separate "Tea" coupon window in the given spec; its Breakfast+Tea coupon covers tea for that shift, and Dinner is its Meal coupon.
- 3rd shift has a standalone Tea window and a separate Breakfast+Tea window, but no Meal window (spec does not define one — configurable by admin per operational needs).
- All windows are stored as configurable data (`shift_meal_windows` table), not hardcoded, so operations can adjust them without a code deployment.
- A scan attempted outside all configured windows for the worker's current shift is rejected with a clear reason.

## 4. Monthly Coupon Allocation Rules

- Monthly working days baseline: **26**.
- Every active worker receives, on the 1st of each month:
  - 26 × Breakfast + Tea coupons
  - 26 × Meal coupons
  - 26 × Tea coupons
  - **Total: 78 coupons/month**
- Allocation is generated by an automated monthly job (cron, 00:05 on the 1st) and is idempotent (safe to re-run).
- Unused coupons **expire at month end** by default. A `carry_forward_enabled` system setting (off by default) allows future policy changes without code changes.
- Per-day cap: max **1 redemption per coupon type per day**, regardless of remaining monthly balance.
- A coupon type already used on the current calendar date cannot be redeemed again the same day, even if the worker's shift crosses midnight (day boundary is the shift's operational day, configurable).

## 5. Functional Requirements

### FR-1 Authentication
- FR-1.1 Worker logs in with Clock Number + Password, or Clock Number + OTP (SMS).
- FR-1.2 Admin/canteen staff log in with email/username + password (+ optional MFA).
- FR-1.3 JWT access tokens (short-lived) + refresh tokens (long-lived, revocable); session timeout after configurable inactivity.
- FR-1.4 Device binding: a worker's active session is tracked per device; admin can force-logout a device (device authentication / anti-sharing control).

### FR-2 QR Scan & Coupon Redemption
- FR-2.1 Worker scans the canteen's permanent QR code from within the app.
- FR-2.2 App/back end resolves: current server time → worker's assigned shift → which coupon type(s) are within a valid window right now.
- FR-2.3 Worker selects exactly one valid coupon type and confirms.
- FR-2.4 Backend re-validates atomically (server-side, not trusting client): shift window, remaining monthly balance, not-already-used-today, QR code validity, — then decrements balance and records a transaction.
- FR-2.5 Duplicate-scan prevention: a second redemption attempt for the same coupon type/day is rejected with the existing transaction shown ("already used at HH:MM").
- FR-2.6 On success, an event is pushed via Socket.IO to the canteen dashboard within ~1 second.

### FR-3 Canteen Real-Time Dashboard
- FR-3.1 Displays, per scan: Worker Name, Clock Number, Department, Shift, Coupon Type, Date, Time, Status, Remaining Coupons, Photo (optional).
- FR-3.2 Live-updating list/feed (Socket.IO), newest first, auto-scroll toggle.
- FR-3.3 Filter by shift/department/coupon type for the current day.

### FR-4 Worker Mobile App
- FR-4.1 Profile screen: name, clock number, department, shift, photo.
- FR-4.2 Home screen: today's available coupons (with countdown to next/current window), remaining monthly balance per type.
- FR-4.3 QR scanner screen using device camera.
- FR-4.4 Coupon history: filterable list of past redemptions.
- FR-4.5 Monthly usage summary (used vs. allocated, per type).
- FR-4.6 Notifications (shift changes, holiday canteen closures, low-balance reminders).
- FR-4.7 Feedback submission (see FR-5).
- FR-4.8 Settings: Dark mode, Language toggle (Marathi / English).

### FR-5 Feedback System
- FR-5.1 After a successful redemption, a feedback popup is offered (skippable).
- FR-5.2 5-star rating, free-text comment, optional photo upload, and category tags: Food Quality, Tea Quality, Breakfast Quality, Cleanliness, Staff Behaviour, Waiting Time, Suggestions.
- FR-5.3 Feedback is linked to the specific transaction (worker, coupon type, date/time) but the aggregate reporting view can be anonymized per admin policy.
- FR-5.4 Admin analytics: average rating (overall/by category/by date range), common complaint keyword trends, charts, monthly summary report.

### FR-6 Admin Dashboard
- FR-6.1 Worker Management: CRUD, bulk import (CSV), assign department/shift, activate/deactivate, reset password.
- FR-6.2 Coupon Management: view/adjust individual balances (with audit trail), trigger manual monthly regeneration (idempotent), configure carry-forward policy.
- FR-6.3 Shift Management: CRUD shifts and their meal windows.
- FR-6.4 Real-Time Scan Monitoring: same feed as canteen dashboard, with admin-level filters.
- FR-6.5 Reports: Daily/Monthly Consumption, Department-wise, Coupon Utilization, Financial Savings (billed-vs-actual), Feedback Analytics — each exportable to Excel and PDF.
- FR-6.6 Menu Management: set daily/weekly menu items per shift/meal.
- FR-6.7 Holiday Management: mark canteen-closed dates; coupons are not consumable/expected on holidays.
- FR-6.8 Notifications: compose and broadcast to all workers or a filtered segment.
- FR-6.9 Role-based access control across all of the above.

### FR-7 Analytics Dashboard
- FR-7.1 KPIs: Daily Breakfast/Meal/Tea counts, department-wise & shift-wise consumption, monthly cost (consumption × per-meal contracted rate), unused-coupon count/%, worker usage %, peak redemption time, feedback rating trend.
- FR-7.2 Visualized via charts (line/bar/pie) with date-range and department/shift filters.

## 6. Non-Functional Requirements

| Category | Requirement |
|---|---|
| Scalability | Support 10,000+ registered workers, 1,000+ concurrent scan-window redemptions (peak shift-change bursts) |
| Performance | Scan validation + dashboard push < 1s p95 under peak load |
| Availability | 99.5% uptime target for canteen operating hours |
| Security | JWT auth, RBAC, TLS everywhere, encrypted secrets, audit logs, rate limiting, duplicate-scan prevention, device binding, input validation on every endpoint |
| Data integrity | Coupon debit is a single atomic DB transaction (row-level lock) to prevent race-condition double-spend under concurrent requests |
| Localization | Marathi + English, switchable at runtime, all worker-facing strings externalized |
| Usability | Large tap targets, ≤3 taps from app open to coupon redemption, Material Design |
| Auditability | Every coupon debit/credit and admin balance override is immutably logged with actor, timestamp, reason |
| Compliance | Worker PII (phone, photo) encrypted at rest; data retention policy configurable |

## 7. System Constraints & Business Rules Summary

1. One coupon of each type usable per worker per day, never more.
2. Redemption only within the worker's current shift's configured meal window.
3. Balances reset to 26/26/26 on the 1st of each month; no negative balances.
4. A single permanent QR code identifies the canteen location; worker identity comes from their authenticated session, not the QR payload.
5. Every transaction is immutable once written (corrections are compensating admin actions with audit trail, never row edits/deletes).

## 10. Acceptance Criteria (Sample)

- AC-1: Given a 1st-shift worker with a full Breakfast+Tea balance, scanning at 08:45 and confirming "Breakfast + Tea" succeeds, balance decrements to 25, and the canteen dashboard shows the entry within 1 second.
- AC-2: The same worker attempting a second Breakfast+Tea redemption the same day is rejected with "Already used today at 08:45".
- AC-3: A 1st-shift worker attempting a Meal redemption at 10:00 (outside 11:30–14:00) is rejected with "Meal is only available 11:30 AM – 02:00 PM".
- AC-4: On 2026-08-01 00:05, all active workers' balances are reset to 26/26/26 regardless of prior month's leftover balance.
- AC-5: Admin exports the August Coupon Utilization Report to Excel and it matches the sum of that month's transaction table.
